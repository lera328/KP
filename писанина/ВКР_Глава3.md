# Глава 3. Реализация и тестирование системы

## 3.1 Реализация серверной части

### 3.1.1 Структура проекта

Серверная часть организована как Django-проект с модульной структурой. Каждый функциональный домен выделен в отдельное приложение Django (app), что обеспечивает чёткое разграничение ответственности и позволяет вносить изменения в один модуль без риска повлиять на остальные.

Структура серверной части имеет следующий вид:

```
backend/
├── config/             — настройки проекта, корневой URL-конфиг
│   ├── settings.py
│   ├── urls.py
│   └── wsgi.py
├── apps/
│   ├── users/          — пользователи, роли, портфолио, аналитика оттока
│   ├── courses/        — курсы, группы, локации
│   ├── attendance/     — занятия, посещаемость, отработки
│   ├── finance/        — абонементы, платежи
│   └── notifications/  — отправка уведомлений (Telegram)
├── manage.py
└── requirements.txt
```

Модели данных описаны с использованием Django ORM. Каждая модель транслируется в таблицу реляционной базы данных, а изменения структуры применяются через систему миграций Django, которая автоматически генерирует SQL-скрипты по изменениям в описании моделей.

### 3.1.2 Реализация аутентификации

Аутентификация реализована на основе JWT-токенов. При отправке логина и пароля на эндпоинт /api/auth/session-login/ сервер проверяет учётные данные, при успехе — генерирует пару токенов (access и refresh) и возвращает их вместе с профилем пользователя. Поддерживается вход как по имени пользователя, так и по адресу электронной почты: если аутентификация по переданному значению как username не прошла, система пытается найти пользователя по полю email и повторяет проверку.

Для защиты административных функций реализован механизм принудительной смены пароля: при создании учётной записи администратором устанавливается флаг must_change_password, и при первом входе пользователь перенаправляется на страницу смены пароля. Доступ к остальным разделам блокируется до завершения этой процедуры.

### 3.1.3 Реализация подсистемы посещаемости

Центральным процессом учебного контура является проведение занятия. Преподаватель открывает карточку занятия в расписании и заполняет форму проведения: вводит тему, описание пройденного материала и домашнее задание, а также отмечает присутствие каждого ученика группы. При сохранении данных сервер одновременно обновляет запись занятия и создаёт записи посещаемости для всех учеников группы. Для учеников с активным абонементом автоматически списывается одно занятие при отметке «Присутствовал».

Логика проведения занятия реализована как единая транзакция: если на любом этапе возникает ошибка (например, у ученика отсутствует абонемент), изменения откатываются, и данные остаются в согласованном состоянии.

### 3.1.4 Реализация подсистемы отработок

Процесс отработки пропуска включает несколько этапов. Преподаватель публикует доступные слоты — занятия с флагом is_makeup_slot, указывая дату, время, локацию и вместимость. Родитель, просматривая посещаемость ребёнка, видит занятия с отметкой «пропуск» и кнопку «Записать на отработку». При нажатии система запрашивает у сервера доступные слоты для данного ученика и отображает их в модальном окне. После выбора слота создаётся запись MakeUpRequest со статусом «Запрошена».

Администратор видит список всех заявок на отработку и может подтвердить выполненную отработку (статус переходит в «Подтверждена»), отклонить заявку (статус сбрасывается, слот освобождается, родитель может выбрать другой) или самостоятельно назначить отработку конкретному ученику.

При создании и подтверждении отработки система отправляет уведомления через Telegram Bot API — родителю и преподавателю соответственно.

### 3.1.5 Реализация генерации портфолио

Портфолио ученика формируется по запросу (кнопка «Скачать PDF» в личном кабинете). Серверный модуль portfolio.py собирает данные из нескольких таблиц: список проектов ученика с изображениями и файлами, количество лайков каждого проекта, история посещённых занятий с оценками, информация о группах и курсах ученика. На основе собранных данных рассчитываются агрегированные показатели: общее количество проектов, число посещённых занятий, суммарное число лайков и средний балл.

Для формирования публичной ссылки на портфолио используется уникальный UUID-токен, привязанный к профилю ученика. По этому токену генерируется QR-код, который включается в PDF-документ. Рендеринг выполняется в два этапа: сначала Django-шаблонизатор формирует HTML-страницу с данными портфолио, затем библиотека WeasyPrint преобразует HTML в PDF с сохранением стилей, изображений и QR-кода.

### 3.1.6 Реализация алгоритма антиотток-аналитики

Алгоритм расчёта риска оттока реализован в модуле churn.py. При обращении к эндпоинту /api/auth/users/churn-risk/ для каждого активного ученика выполняется расчёт по набору критериев, описанных в разделе 2.5. Результат возвращается в виде JSON-массива объектов, каждый из которых содержит идентификатор и имя ученика, метрики посещаемости, информацию об абонементе, итоговый уровень риска и массив текстовых причин.

Алгоритм не требует предварительного расчёта или хранения промежуточных данных — все метрики вычисляются на лету по текущему состоянию базы данных. Это гарантирует актуальность результатов при каждом обращении. При росте числа учеников и необходимости ускорения запроса предусмотрена возможность кэширования результатов с периодическим обновлением.

## 3.2 Реализация клиентской части

### 3.2.1 Архитектура фронтенд-приложения

Клиентское приложение построено на React 18 с использованием функциональных компонентов. Состояние аутентификации управляется через React Context (AuthContext), который хранит профиль текущего пользователя, предоставляет методы входа и выхода и функцию проверки принадлежности к роли (hasRole). Все защищённые маршруты обёрнуты в компонент ProtectedRoute, который проверяет наличие аутентификации и при необходимости перенаправляет на страницу входа. Дополнительно используется компонент RoleRoute, ограничивающий доступ к разделам по роли.

Взаимодействие с серверным API инкапсулировано в сервисном модуле api.js. Он реализует централизованную обработку HTTP-запросов: автоматическое добавление JWT-токена в заголовок Authorization, обработку ошибок 401 (истечение сессии — очистка токена и перенаправление на страницу входа), парсинг JSON-ответов и отправку данных форм (FormData). Такой подход исключает дублирование логики работы с API в каждом компоненте.

### 3.2.2 Компоненты интерфейса

Структура компонентов организована по функциональному принципу. Каждый экран системы реализован как отдельный React-компонент, размещённый в директории components/. Ниже описаны ключевые компоненты.

**AppLayout** — базовый компонент-обёртка, формирующий общую структуру страницы: верхнюю панель с названием раздела, боковую навигацию (для администратора и преподавателя) или нижнюю панель навигации (для ученика и родителя). Поддерживает режим kidMode для детского интерфейса.

**Dashboard** — главная страница после входа. В зависимости от роли отображает разный набор информации: для администратора — ключевые метрики (количество учеников, занятий, риски оттока), для преподавателя — ближайшие занятия, для родителя — карточки детей с информацией о посещаемости и балансе, для ученика — прогресс и ближайшее расписание.

**ParentAttendance** — журнал посещаемости в кабинете родителя. Отображает список занятий каждого ребёнка с отметками присутствия, оценками и комментариями. Записи с отметкой «пропуск» содержат кнопку записи на отработку. Каждая строка кликабельна — при нажатии открывается модальное окно с подробным описанием занятия.

**ProjectsFeed** — общая лента проектов, доступная всем ролям. Отображает карточки проектов с изображениями, описанием, количеством лайков и кнопкой голосования. Лучший проект (с максимальным числом лайков) выделяется в отдельный блок. Для учеников и родителей реализованы фильтры: «Все проекты» и «Мои проекты» (или «Проекты моих детей»).

**AdminChurnRisk** — таблица учеников с рисками оттока для администратора. Отображает имя ученика, группу, количество пропусков подряд, посещаемость за 30 дней, остаток занятий на абонементе, уровень риска (цветовая индикация) и текстовые причины. Поддерживается фильтрация по уровню риска.

**Portfolio** — страница портфолио ученика с отображением проектов, статистики, посещённых занятий и кнопкой скачивания PDF-версии.

## 3.3 Развёртывание системы

Развёртывание системы осуществляется средствами Docker Compose. Конфигурационный файл docker-compose.yml описывает три сервиса:

1. **db** — контейнер с PostgreSQL 14. Данные базы хранятся в именованном томе Docker, что обеспечивает их сохранность при перезапуске контейнера. Параметры подключения (имя базы, пользователь, пароль) задаются через переменные окружения.

2. **backend** — контейнер с серверным приложением Django. При запуске автоматически применяются миграции базы данных и запускается dev-сервер на порту 8000. Исходный код монтируется как том, что позволяет вносить изменения без пересборки образа в режиме разработки.

3. **frontend** — контейнер с клиентским приложением React. Запускается dev-сервер Vite на порту 5173 с проксированием API-запросов на контейнер backend. Аналогично серверной части, исходный код монтируется как том для горячей перезагрузки при разработке.

Для запуска системы достаточно выполнить одну команду: `docker compose up --build`. После старта всех контейнеров клиентское приложение доступно по адресу http://localhost:5173, серверное API — по адресу http://localhost:8000.

## 3.4 Тестирование

Тестирование системы проводилось на нескольких уровнях.

**Функциональное тестирование API.** Каждый эндпоинт серверной части проверялся на корректность обработки запросов с валидными и невалидными данными, соответствие HTTP-кодов ответов (200, 201, 400, 401, 403, 404), корректность структуры JSON-ответов и соблюдение ролевых ограничений (попытка доступа к административному эндпоинту от имени ученика должна возвращать 403).

**Интеграционное тестирование.** Проверялись сквозные сценарии, затрагивающие несколько модулей:
- полный цикл отработки: создание пропуска → публикация слота преподавателем → запись на отработку родителем → подтверждение администратором → списание занятия с абонемента;
- цикл портфолио: добавление проекта учеником → загрузка изображения → голосование → генерация PDF с корректными данными;
- аналитика оттока: создание серии пропусков → проверка корректности расчёта уровня риска.

**Тестирование пользовательского интерфейса.** Для каждой роли (администратор, преподаватель, родитель, ученик) проверялись: корректность отображения навигации, доступность только разрешённых разделов, работоспособность основных сценариев (вход, просмотр данных, выполнение действий), отображение ошибок при некорректных действиях.

**Тестирование совместимости.** Интерфейс проверялся в браузерах Chrome, Firefox и Edge на разрешениях экрана от 375px (мобильное устройство) до 1920px (настольный монитор).

Для начального наполнения базы данных тестовыми данными разработан скрипт seed_demo.py, который создаёт пользователей всех ролей, курсы, группы, занятия, записи посещаемости, абонементы, проекты и лайки. Это позволяет воспроизводить типовые сценарии использования без ручного ввода данных.

В результате тестирования выявленные дефекты были устранены. Система обеспечивает корректную работу по всем функциональным требованиям, описанным в разделе 1.2.
