# Глава 2. Проектирование автоматизированной системы для школы программирования

## 2.1 Архитектурное решение

Архитектура разрабатываемой системы построена по принципу многоуровневого клиент-серверного взаимодействия с чётким разделением ответственности между уровнями.

Клиентский уровень представлен одностраничным веб-приложением (SPA), работающим в браузере пользователя. Выбор SPA-архитектуры обусловлен тем, что система рассчитана на частое взаимодействие пользователя с интерфейсом — переключение между разделами, просмотр журналов, выставление оценок, работа с лентой проектов — и перезагрузка страницы при каждом действии снижала бы удобство работы. SPA загружает основной код при первом обращении, а далее обменивается с сервером только данными в формате JSON, что сокращает объём сетевого трафика и обеспечивает отзывчивый интерфейс.

Серверный уровень реализован в виде REST API, отвечающего за бизнес-логику, аутентификацию, авторизацию, работу с базой данных и интеграцию с внешними сервисами. Все операции выполняются через HTTP-запросы к набору эндпоинтов, каждый из которых принимает и возвращает данные в формате JSON. Такой подход упрощает тестирование серверной логики отдельно от интерфейса и позволяет в дальнейшем подключать к тому же API мобильное приложение или сторонние интеграции без доработки серверной части.

Уровень хранения данных реализован через реляционную СУБД, обеспечивающую целостность данных, поддержку транзакций и возможность выполнения сложных аналитических запросов — например, для расчёта рисков оттока учеников или формирования финансовой отчётности.

Дополнительно в архитектуре присутствует контур интеграции с внешними сервисами. На текущем этапе реализована отправка уведомлений через Telegram Bot API — при создании записи на отработку, подтверждении платежа и других событиях система направляет сообщение в Telegram-чат родителя или преподавателя. Архитектура допускает подключение дополнительных каналов (email, SMS) без изменения основной логики.

Для развёртывания системы используется контейнеризация. Каждый компонент — серверное приложение, клиентское приложение и база данных — запускается в отдельном контейнере, что обеспечивает воспроизводимость окружения и упрощает перенос системы между средами (локальная разработка, тестовый сервер, промышленная эксплуатация).

## 2.2 Структура функциональных модулей

Серверная часть системы разбита на четыре предметных модуля, каждый из которых инкапсулирует модели данных, бизнес-логику и API-эндпоинты, относящиеся к соответствующей функциональной области. Такое разделение повторяет доменную структуру, выявленную в ходе анализа требований, и позволяет вести разработку и тестирование каждого модуля независимо.

**Модуль «Пользователи и роли» (users).** Отвечает за аутентификацию, управление профилями и ролевое разграничение доступа. В системе определены четыре роли: администратор, преподаватель, родитель и ученик. Каждый пользователь может иметь одну или несколько ролей, что позволяет, например, администратору совмещать функции менеджера. Между родителем и учеником реализована связь «один ко многим» — один родитель может быть привязан к нескольким детям. Этот же модуль содержит логику генерации цифрового портфолио (формирование контекста данных и рендеринг PDF), алгоритм расчёта риска оттока учеников и управление проектами учеников (создание, редактирование, загрузка изображений и файлов, механизм лайков).

**Модуль «Курсы и группы» (courses).** Управляет справочником курсов, учебными группами, привязкой учеников и преподавателей к группам, а также справочником локаций (точек проведения занятий). Группа привязана к конкретному курсу, имеет расписание (день недели и время) и список учеников и преподавателей, связанных с ней через промежуточные таблицы. Отдельно хранятся комментарии преподавателей о группах.

**Модуль «Посещаемость и отработки» (attendance).** Реализует полный цикл учёта занятий: создание уроков по расписанию, отметку посещаемости с оценками и комментариями преподавателя, проведение занятий с фиксацией темы и описания. Подсистема отработок позволяет преподавателю публиковать доступные слоты, родителю — выбрать слот и записать ребёнка, администратору — подтвердить, отклонить или самостоятельно назначить отработку. Каждая запись на отработку проходит через состояния: «Запрошена» → «Проведена» → «Подтверждена администратором».

**Модуль «Финансы» (finance).** Управляет абонементами учеников и платежами. Абонемент содержит количество оплаченных занятий (или период действия) и привязан к конкретному ученику — при этом у ученика в каждый момент времени может быть только один активный абонемент, что обеспечивается ограничением на уровне базы данных. Модуль также реализует механизм платёжных намерений (PaymentIntent) с тремя тарифными планами (месяц, полгода, год) и статусами прохождения оплаты.

## 2.3 Проектирование базы данных

Схема базы данных спроектирована на основе диаграмм классов, представленных в разделе 1.4, и реализована средствами ORM фреймворка Django. Ниже описаны ключевые сущности и связи между ними.

Центральной сущностью является **User** — расширение стандартной модели пользователя Django. Помимо базовых атрибутов (имя, фамилия, email, хеш пароля), добавлены поля для хранения номера телефона, идентификатора Telegram-чата и флага обязательной смены пароля при первом входе. Роли пользователей реализованы через отдельную таблицу **Role** со связью «многие ко многим», что позволяет одному пользователю совмещать несколько ролей.

Профили ученика (**StudentProfile**) и родителя (**ParentProfile**) реализованы как отдельные таблицы со связью «один к одному» к User. Профиль ученика хранит уникальный токен портфолио (UUID), используемый для формирования публичной ссылки на портфолио. Профиль родителя содержит связь «многие ко многим» с профилями учеников, что позволяет привязать к одному родителю нескольких детей.

Учебный процесс представлен цепочкой сущностей: **Course** → **Group** → **Lesson** → **AttendanceRecord**. Курс содержит название и описание образовательной программы. Группа привязана к курсу и имеет расписание (день недели, время), список учеников и преподавателей. Связь учеников и преподавателей с группами реализована через промежуточные таблицы **GroupStudent** и **GroupTeacher** с ограничением уникальности пары (группа, пользователь). Каждая группа привязана к локации (**Location**) — конкретному адресу проведения занятий.

Занятие (**Lesson**) содержит дату и время проведения, ссылку на группу и преподавателя, тему из справочника (**LessonTopic**) или свободную тему, введённую при проведении. Для слотов отработки предусмотрен флаг is_makeup_slot и параметр вместимости (makeup_capacity).

Запись посещаемости (**AttendanceRecord**) фиксирует факт присутствия, пропуска или отработки ученика на конкретном занятии. Пара (занятие, ученик) уникальна. Дополнительно хранятся оценка, комментарий преподавателя и признак списания занятия с абонемента.

Заявка на отработку (**MakeUpRequest**) связывает запись о пропуске с конкретным слотом отработки. Она проходит через три статуса: запрошена, проведена, подтверждена. Хранятся ссылки на утвердившего администратора и дату подтверждения.

Финансовый контур включает таблицу **Subscription** (абонемент) с количеством оставшихся занятий, периодом действия и статусом активности, таблицу **Payment** (факт оплаты) и **PaymentIntent** (намерение оплаты с тарифным планом и статусом обработки).

Подсистема проектов и портфолио состоит из таблиц **StudentProject** (проект ученика с названием, описанием, ссылкой), **StudentProjectImage** (изображения проекта), **StudentProjectFile** (файлы проекта) и **StudentProjectLike** (лайки с ограничением уникальности пары «проект — пользователь»).

## 2.4 Проектирование REST API

Взаимодействие клиентского приложения с сервером осуществляется через REST API. Все запросы и ответы используют формат JSON. Аутентификация реализована на основе JWT-токенов (JSON Web Token): при входе пользователь получает пару токенов (access и refresh), access-токен передаётся в заголовке Authorization каждого последующего запроса. Время жизни access-токена ограничено, refresh-токен позволяет получить новый access без повторного ввода пароля.

Разграничение доступа реализовано на уровне каждого эндпоинта: проверяется не только наличие валидного токена, но и принадлежность пользователя к требуемой роли. Например, эндпоинт просмотра посещаемости ребёнка доступен только пользователям с ролью «родитель», а управление группами — только администраторам.

API системы разбит на четыре группы маршрутов, соответствующих функциональным модулям.

**Группа «Аутентификация и пользователи» (/api/auth/).** Включает эндпоинты входа в систему, выхода, получения и обновления профиля, смены и сброса пароля, создания и редактирования пользователей (для администратора), получения списка детей родителя, просмотра посещаемости и биллинга родителя, управления проектами ученика, генерации портфолио в формате PDF, просмотра ленты проектов и механизма лайков, а также аналитики риска оттока и метрик для дашборда администратора.

**Группа «Курсы и группы» (/api/courses/).** Предоставляет CRUD-операции для курсов, групп и локаций, а также возможность добавления комментариев к группам.

**Группа «Посещаемость и отработки» (/api/attendance/).** Охватывает работу с занятиями (создание, просмотр, проведение), отметку посещаемости, настройку группового расписания, управление слотами отработок (публикация, обновление), создание и подтверждение заявок на отработку, а также расчёт зарплаты преподавателя.

**Группа «Финансы» (/api/finance/).** Реализует просмотр и управление абонементами и платежами через стандартные REST-операции.

## 2.5 Алгоритм расчёта риска оттока

Одним из ключевых функциональных требований является автоматическое выявление учеников, которые с высокой вероятностью могут прекратить обучение. Для решения этой задачи разработан алгоритм скоринга, анализирующий поведение каждого ученика по нескольким параметрам за скользящее окно в 30 дней.

Алгоритм выполняется при обращении администратора к соответствующему разделу и проходит следующие этапы для каждого активного ученика:

1. Из базы данных извлекаются последние записи посещаемости ученика, отсортированные по дате от новых к старым.

2. Вычисляется количество пропусков подряд (consecutive absences) — начиная с последнего занятия, считается непрерывная серия пропусков. Три и более пропуска подряд соответствуют высокому уровню риска, два — среднему.

3. Рассчитывается доля посещённых занятий за последние 30 дней (attendance rate). Если посещаемость ниже 60%, это рассматривается как дополнительный фактор риска.

4. Проверяется состояние абонемента: отсутствие активного абонемента в сочетании с пропусками повышает риск до высокого уровня; истечение абонемента в ближайшие 7 дней или нулевой остаток занятий — до среднего.

5. Анализируется давность последнего посещения: если ученик не появлялся на занятиях более 21 дня, это считается признаком риска.

По совокупности факторов каждому ученику присваивается итоговый уровень: low (низкий), medium (средний) или high (высокий). К каждому уровню прикрепляется текстовое описание причин, позволяющее администратору оперативно понять ситуацию — например, «3 пропуска подряд», «Абонемент истекает через 5 дн.», «Посещаемость за 30 дней 42%».

Результаты сортируются по убыванию уровня риска и выводятся на дашборд администратора в виде таблицы с возможностью быстрого перехода к карточке ученика.

## 2.6 Проектирование пользовательского интерфейса

Интерфейс системы спроектирован с учётом того, что пользователи относятся к четырём принципиально разным категориям: администраторы, преподаватели, родители и ученики (дети 6–14 лет). Это накладывает разные требования к визуальному оформлению и навигации.

Для администраторов и преподавателей используется стандартный деловой интерфейс с боковой навигационной панелью, таблицами данных, модальными окнами для редактирования и графиками на дашборде. Визуальный стиль выдержан в нейтральной цветовой гамме, компоновка рассчитана на работу с десктопного устройства.

Для учеников и родителей разработан отдельный «детский» режим интерфейса с закруглёнными элементами, увеличенными кнопками, яркой цветовой палитрой и нижней навигационной панелью, привычной пользователям мобильных приложений. Переключение между режимами происходит автоматически на основании роли текущего пользователя.

Маршрутизация внутри приложения организована по ролевому принципу: после аутентификации пользователь попадает на дашборд, соответствующий его роли, а пункты навигации определяются набором доступных функций. Администратор видит разделы «Пользователи», «Группы», «Расписание», «Финансы», «Отработки», «Уведомления», «Аналитика оттока». Преподаватель — «Расписание», «Группы», «Зарплата», «Слоты отработок». Родитель — «Дети», «Посещаемость», «Оплата». Ученик — «Расписание», «Проекты», «Портфолио», «Баланс».

Общая для всех ролей страница «Лента проектов» отображает работы учеников с возможностью голосования (лайков). Для учеников и родителей реализованы фильтры: ученик может отобразить только свои проекты, родитель — только проекты своих детей. Лучший проект (с наибольшим числом лайков) выделяется в отдельный блок в верхней части страницы.

## 2.7 Выбор программных средств и обоснование технологического стека

### 2.7.1 Серверная часть

В качестве языка программирования серверной части выбран **Python** версии 3.11. Выбор обусловлен наличием развитой экосистемы библиотек для веб-разработки, работы с данными и генерации документов, а также широким применением этого языка в образовательных и прикладных проектах, что обеспечивает доступность специалистов для дальнейшего сопровождения системы.

Основным веб-фреймворком выбран **Django 4.2** в сочетании с **Django REST Framework 3.14**. Django предоставляет встроенную ORM для работы с базой данных, систему миграций, механизм аутентификации и административную панель. Django REST Framework добавляет инструменты для построения REST API: сериализаторы, представления, маршрутизацию, пагинацию и систему разрешений. Связка Django + DRF является одним из наиболее распространённых решений для разработки серверных приложений на Python и хорошо документирована.

Для аутентификации используется библиотека **SimpleJWT**, реализующая выдачу и верификацию JWT-токенов. Этот подход не требует хранения сессий на сервере, что упрощает горизонтальное масштабирование.

Для генерации PDF-портфолио применяется библиотека **WeasyPrint**, позволяющая преобразовывать HTML-шаблоны в PDF-документы с сохранением стилей CSS. QR-код для публичной ссылки на портфолио генерируется средствами библиотеки **qrcode**.

В качестве СУБД выбрана **PostgreSQL 14**. Это реляционная база данных с открытым исходным кодом, поддерживающая сложные запросы, транзакции, индексацию и ограничения целостности. PostgreSQL хорошо интегрируется с Django ORM и широко применяется в промышленных проектах.

### 2.7.2 Клиентская часть

Клиентское приложение реализовано на библиотеке **React 18** с использованием функциональных компонентов и хуков (useState, useEffect, useMemo, useContext). React обеспечивает компонентный подход к построению интерфейса, декларативное описание представления и эффективное обновление DOM через механизм виртуального DOM.

Для маршрутизации используется **React Router 6**, для стилизации — фреймворк **Bootstrap 5** с дополнительными CSS-модулями для «детского» режима интерфейса. Взаимодействие с серверным API выполняется через встроенный **Fetch API** с обёрткой, реализующей автоматическое добавление токена авторизации, обработку ошибок и перенаправление при истечении сессии.

Сборка проекта выполняется инструментом **Vite**, обеспечивающим быстрый запуск dev-сервера с горячей перезагрузкой модулей (HMR) и оптимизированную сборку для промышленного развёртывания.

### 2.7.3 Инфраструктура

Для контейнеризации и развёртывания используется **Docker** с оркестрацией через **Docker Compose**. Конфигурация описывает три сервиса: PostgreSQL (база данных), Django (серверная часть) и Vite/React (клиентская часть). Каждый сервис запускается в изолированном контейнере с собственным набором зависимостей, что исключает конфликты версий и обеспечивает идентичность окружения на всех этапах разработки и эксплуатации.

Контроль версий исходного кода осуществляется с помощью системы **Git** с удалённым репозиторием на платформе **GitHub**.

### 2.7.4 CASE-средства

Для проектирования и разработки применялись следующие инструментальные средства:

- **Visual Studio Code** — основная среда разработки для работы с серверным и клиентским кодом;
- **pgAdmin** — визуальное администрирование базы данных PostgreSQL, просмотр и редактирование данных;
